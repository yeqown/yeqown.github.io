    cgroup 自上而下

    September 9, 2026 DRAFT
    架构, 源码分析
    Linux, Cgroup, 容器, 资源管理, Kubernetes

    我最初只把 cgroup 理解成 Kubernetes resources.requests 和 resources.limits 背后的实现。这个理解没有错，但它跳过了真正有意思的部分：为什么 CPU request 最后成了一个相对权重，CPU limit 却是一段时间配额；为什么内存达到上限会触发回收甚至 OOM，而不是像 CPU 一样暂停一会儿；如果自己写一个任务编排器，又该把哪些概念放进公开 API？

    Kubernetes 的版本变化把这些问题推到了眼前。cgroup v2 在 Kubernetes v1.25 进入 Stable；v1.31 将 cgroup v1 支持转入维护模式；从 v1.35 开始，cgroup v1 被正式标记为 deprecated，kubelet 默认不再在 v1 节点启动。

    本文从一个自研工作负载系统开始，依次回答三个问题：上层资源 API 应该表达什么，cgroup 在 Linux 内核里怎样完成这些约束，以及 v1 的哪些设计最终把整个生态推向了 v2。

    阅读边界

    • cgroup v2 的接口和源码入口以 Linux v6.16 为参照；这些核心语义在相邻版本中较稳定，但具体文件仍取决于内核配置和启用的 controller。
    • 本文不依赖手边已有 Linux 环境。命令用于说明接口和观测方法，展示的值来自文中的配置推导，不冒充性能实测。
    • Kubernetes 只用来引出问题并提供一个对照。正文讨论的设计同样适用于批处理系统、容器管理器、进程托管服务和 systemd unit。

    1. 先站到 cgroup 上面#

    1.1 资源配置与职责边界#

    先看最熟悉的配置：

    resources:
  requests:
    cpu: 500m
    memory: 512Mi
  limits:
    cpu: "2"
    memory: 1Gi

    它看起来只有四个数字，实际跨越了两套系统：

    决策 回答的问题 典型执行者 cgroup 是否参与
    放置与准入 哪台机器还能接收这个工作负载 调度器、quota/admission 模块 不直接参与
    节点内资源分配 进程已经运行后，怎样竞争和限制资源 node agent、容器运行时、Linux 内核 参与最终执行

    CPU request 会参与调度，在节点上通常还会被转换成竞争时的 CPU 权重；CPU limit 会转换成带周期的带宽上限。memory request 主要是调度承诺，在 cgroup v2 上也可以作为 memory.min 或 memory.low 的输入；memory limit 则会落到硬边界。相同的 request/limit 外观，背后并不是一套通用算法。

    因此，cgroup 不知道什么是 Pod，也不会替调度器判断一台机器能否再放一个任务。它接受的对象是进程和层级，接受的参数是权重、上限、保护值等。把业务语义翻译成这些参数，是用户态资源管理器的职责。

    Kubernetes 不是使用 cgroup 的唯一方式。把几套接口按层次排开，边界会更清楚：

    系统或接口 面向用户的对象 资源表达 本机执行者 它没有负责什么
    Kubernetes Pod、Container CPU/内存 request 与 limit，Pod QoS 等 kubelet、CRI runtime cgroup 不参与跨节点调度
    Nomad Allocation、Task cpu/cores、memory、memory_max 等 Nomad client 与 task driver 字段是否能精确执行取决于 OS 和 driver
    systemd Slice、Service、Scope CPUWeight、CPUQuota、MemoryLow、MemoryHigh、MemoryMax 等 systemd PID 1 不替应用设计跨机器资源模型
    OCI Runtime Spec Container linux.resources、cgroupsPath runc、crun 等 OCI runtime 它是本机运行契约，不是调度 API
    cgroupfs cgroup 目录中的进程 cpu.max、memory.high、io.max 等文件 Linux 内核 不提供业务对象、准入、重试或状态机

    这几层不能随意互换。直接把 cpu.max 暴露给业务用户，会让 API 绑定 Linux 版本和运行时细节；只提供一个模糊的 resources: small，node agent 又无法判断应该写哪些 controller 文件。比较稳妥的分界是：公开 API 表达资源意图，节点侧生成一份可观测的执行计划，backend adapter 再负责 systemd、OCI 或 cgroupfs 的具体写入。

    1.2 从 ResourceSpec 到 ResourcePlan#

    假设要写一个运行转码任务的系统。下面不是一份通用标准，而是一套可以继续演进的起点：

    apiVersion: runtime.example.io/v1alpha1
kind: Workload
metadata:
  name: transcode-7f3a
  tenant: team-video
spec:
  command: ["transcoder", "--input", "/data/input.mp4"]
  resources:
    cpu:
      request: 500m
      limit: "2"
    memory:
      request: 512Mi
      protection: BestEffort
      throttleAt: 768Mi
      limit: 1Gi
      swapLimit: 0
    io:
      - volume: scratch
        writeBps: 50Mi
    pids:
      limit: 256
  oom:
    scope: Workload

    这里刻意没有 cpu.weight、设备号 259:0 或 cgroup 目录路径。公开字段先把语义说清楚：

    字段 对用户的承诺 节点侧可能的实现
    cpu.request 调度时预留容量；争用时获得相对份额 admission accounting + cpu.weight
    cpu.limit 一段时间内可使用的平均 CPU 带宽上限 cpu.max
    memory.request 调度时预留内存，并按 protection 策略提供回收保护 admission accounting + 可选的 memory.low/memory.min
    memory.throttleAt 超过该值后允许回收和降速，不立刻杀进程 memory.high
    memory.limit 工作负载可占用内存的最终边界 memory.max
    memory.swapLimit 单独约束该组可用的 swap memory.swap.max
    io[].volume 对稳定的 volume 名称限速 node agent 将 volume 解析为块设备，再写 io.max
    pids.limit 限制可创建的内核 task 数量 pids.max
    oom.scope OOM 时维持工作负载完整性，避免只杀掉随机子进程 memory.oom.group

    memory.request 是否真的写入保护边界，必须是显式策略。memory.low 和 memory.min 都受祖先节点的保护额度约束；父级没有分配额度时，叶子上写一个漂亮的数字也无法兑现承诺。要提供 Guaranteed 一类策略，准入层就必须核算整条祖先链，而不是只检查当前机器还有多少空闲内存。

    CPU 权重也不应该成为公开契约。cpu.weight 只表示同一父节点下活跃兄弟之间的比例，而且 v1 cpu.shares 到 v2 weight 的转换并非恒等映射。OCI runtime 在 2026 年还调整过这套转换公式。如果监控系统需要知道最终权重，应从 workload status 或本机运行时读取，而不是从 request 反推。

    节点侧可以把公开配置编译成 ResourcePlan。假设这个系统规定 1000m CPU 对应默认 weight 100，那么上面的任务会生成如下计划：

    backend: cgroup-v2
path: team-video/transcode-7f3a
files:
  cpu.weight: "50"
  cpu.max: "200000 100000"
  memory.low: "536870912"
  memory.high: "805306368"
  memory.max: "1073741824"
  memory.swap.max: "0"
  memory.oom.group: "1"
  io.max: "259:0 wbps=52428800"
  pids.max: "256"

    ResourcePlan 应该进入工作负载 status 和审计日志，而不是执行完就丢掉。这样用户能查到系统最终应用了什么，backend 也能替换：systemd backend 生成 transient scope/service 属性，OCI backend 生成 linux.resources 与 cgroupsPath。只有资源管理器确实拥有一棵委托子树时，才直接操作 cgroupfs。

    cpu.max: 200000 100000 表示每 100000 微秒最多使用 200000 微秒 CPU 时间，即平均 2 个 CPU。它不表示绑定两个固定 CPU，也不阻止任务短时间在更多 CPU 上并行。若要固定 CPU 集合，需要另行设计独占或亲和性 API，并交给 cpuset controller。

    I/O 计划里的 259:0 也不该由用户填写。块设备号会随节点和挂载关系变化，node agent 应在启动与设备变更时解析 scratch，把稳定的 volume 身份翻译为当前设备。如果 volume 最后落到网络文件系统、device mapper 或共享 inode 上，系统还要明确说明哪些限制能生效，哪些只能尽力而为。

    1.3 层级、所有权与生命周期#

    cgroup 的资源约束沿树向下生效。系统里的租户、任务和容器如果需要不同层次的总预算，就应该出现在树中：

    myagent.service/                 systemd 委托边界
├── manager/                    node agent 自己的进程
└── tenants/                    结构节点，无进程
    └── team-video/             租户总预算，无进程
        └── transcode-7f3a/     工作负载总预算，无进程
            ├── main/           转码进程
            └── metrics/        监控 sidecar 进程

    team-video 可以限制整个租户，transcode-7f3a 可以限制任务总量，main 和 metrics 再分配任务内部的资源。父级限制不会被子级覆盖；子级只能在拿到的资源中继续分配。

    这棵树还体现了 v2 的 no internal process 约束：一个非 root 的 domain cgroup 如果要把 CPU、内存或 I/O controller 分发给子节点，它自己不能同时放进程。node agent 因此待在 manager/ 叶子里，结构节点只负责分配资源。在 systemd 上，服务应通过 Delegate=yes 获得子树；较新的 systemd 还可以用 DelegateSubgroup= 把管理进程直接放进指定子组。

    一次可靠的启动可以按下面的顺序进行：

    1. 获取 cgroup 子树。systemd 主机通过 transient unit 或带 Delegate=yes 的 service/scope 取得所有权；非 systemd 环境才考虑由 agent 管理约定好的 cgroup2 子树。
    2. 读取 cgroup.controllers，确认 CPU、memory、I/O、pids 等能力确实可用。API 中无法支持的字段应该进入 status，不能静默忽略。
    3. 创建空的结构节点，把管理进程放到独立叶子，然后从上到下写 cgroup.subtree_control。父级未启用的 controller，子级无法自行启用。
    4. 先写父级预算，再写工作负载与容器级参数。多个 controller 文件之间没有事务，失败时要保留阶段状态并执行幂等回滚。
    5. 让目标进程从出生时就位于目标 cgroup。优先交给 systemd/OCI runtime，或使用 clone3(CLONE_INTO_CGROUP)；“先 exec，再把 PID 移过去”会留下短暂逃逸窗口。
    6. 运行期间读取统计、事件和 pressure，接受资源更新并持续校正漂移。调整 memory.max 等状态型资源时，要处理同步回收和 OOM 风险。
    7. 停止时先阻止新任务，必要时写 cgroup.kill，等待 cgroup.events 的 populated 0，最后从叶子向上删除空目录。

    一个可用的顶层 API 还要有 status，记录 backend 类型、实际 cgroup 路径、生效值、缺失能力、最近一次 reconcile 错误和 pressure/OOM 事件。例如：

    status:
  observedGeneration: 7
  backend:
    type: cgroup-v2
    path: /myagent.service/tenants/team-video/transcode-7f3a
  effective:
    cpu.weight: "50"
    cpu.max: "200000 100000"
    memory.max: "1073741824"
  conditions:
    - type: ResourcesApplied
      status: "True"
    - type: ControllerAvailable
      resource: io
      status: "True"
  events:
    memoryHigh: 12
    oomKill: 0

    更新规则也属于 API 契约。request 变化要重新经过准入，必要时触发迁移；CPU weight 和 limit 通常可以原地更新；向下调整 memory.max 则可能让执行写操作的线程同步回收，甚至触发 memcg OOM。由于多个 controller 文件之间没有事务，status 需要用 observedGeneration 和 phase 区分“配置已接收”“正在应用”和“已经生效”。

    2. cgroup 在 Linux 系统架构中的位置#

    2.1 从 cgroupfs 到内核 controller#

    Linux 内核文档对 cgroup 的定义很克制：它把进程组织成层级，并沿层级分配系统资源。实现也分成两部分：

    • cgroup core 管进程属于哪个组、组之间的父子关系、controller 的启停、委托、迁移和公共统计。
    • controller 管某一类资源。CPU controller 接入调度器，memory controller 接入内存记账与回收，I/O controller 接入块层，pids controller 接入 fork()/clone() 路径。

    cgroupfs 是两者暴露给用户态的控制面。它看起来像目录和文件，但写进去的内容不会保存成普通磁盘文件；VFS 将读写交给 kernfs 和 cgroup/controller 的回调。早期 cgroup 没有为这些操作增加一套专用系统调用，mkdir、rmdir、read、write 和文件通知就是主要 API。后来 clone3(CLONE_INTO_CGROUP) 补上了“让子进程直接出生在目标组”这个启动能力。

    cgroup 所在的层次由此很明确：它不是调度器上方一个独立的资源模拟层，也不属于容器运行时。它在内核中维护统一的进程分组，并向调度器、内存管理、块 I/O 等子系统提供 controller 状态和钩子。容器运行时只是用户态调用者之一。

    沿着这层关系继续往下看，Linux v6.16 的 task_struct 中有一条指向 css_set 的 RCU 指针：

    // include/linux/sched.h
struct task_struct {
    // ...
    struct css_set __rcu *cgroups;
    struct list_head cg_list;
    // ...
};

    css 是 cgroup subsystem state 的缩写。几个关键对象可以简化成：

    // include/linux/cgroup-defs.h，字段经过裁剪
struct cgroup_subsys_state {
    struct cgroup *cgroup;
    struct cgroup_subsys *ss;
    struct cgroup_subsys_state *parent;
};

struct css_set {
    struct cgroup_subsys_state *subsys[CGROUP_SUBSYS_COUNT];
    struct cgroup *dfl_cgrp;
    struct list_head tasks;
};

struct cgroup {
    struct kernfs_node *kn;
    struct cgroup_subsys_state __rcu *subsys[CGROUP_SUBSYS_COUNT];
    u16 subtree_control;
};

    可以沿这条链理解它们：

    task_struct
    -> css_set
        -> CPU controller 的 cgroup_subsys_state
        -> memory controller 的 cgroup_subsys_state
        -> I/O controller 的 cgroup_subsys_state
        -> ...

    多个进程如果拥有同一组 controller 归属，可以共享 css_set，不用在每个 task_struct 中重复保存整套指针。对 v2 来说，一个进程在统一层级里只有一条 cgroup 路径；但某个 controller 可能没有在该节点启用，此时 css_set 中对应项可以指向最近的有效祖先状态。

    struct cgroup_subsys 则是一张 controller 回调表，包含状态创建和销毁、进程 attach、fork/exit 以及默认层级文件表 dfl_cftypes。controller 用 cftype 注册自己的接口文件。例如 CPU 注册 weight 和 max 后，cgroup core 会以 cpu. 前缀把它们呈现为 cpu.weight 和 cpu.max。

    再用两个常见写操作把这些对象串起来。

    把 PID 写入 cgroup.procs 时，内核大致经过：

    write(cgroup.procs)
  -> cgroup_procs_write()
  -> 检查目标 cgroup、权限与委托边界
  -> cgroup_attach_task()
  -> 切换 css_set，并调用相关 controller 的 attach 回调

    写 cpu.max 时走的是另一条路：

    write(cpu.max, "200000 100000")
  -> kernfs 找到 CPU controller 的 cftype
  -> cpu_max_write()
  -> 解析 quota/period
  -> tg_set_cfs_bandwidth()
  -> 更新调度器 task_group 的带宽状态

    所以 cgroupfs 不是一个不断轮询并杀进程的后台服务。文件写入直接改变内核对象，之后资源子系统在自己的热路径上记账和执行。

    2.2 CPU：权重和上限是两种模型#

    CPU controller 最容易被 request/limit 这组词误导。v2 提供的两个主要旋钮互不替代。

    cpu.weight：只在竞争时分配比例#

    cpu.weight 的范围是 1 到 10000，默认值为 100。假设同一父 cgroup 下只有两个一直 runnable 的子组，weight 分别是 50 和 100，那么在 CPU 饱和时，它们期望得到的时间比例约为 1:2。

    这里有三个限制条件：

    1. 它比较的是兄弟节点，不是全局优先级。把不同父节点下的两个 weight 直接相比没有意义。
    2. 它是 work-conserving 的。另一个组没有任务可运行时，weight 50 的组仍可使用全部空闲 CPU。
    3. 它不承诺 500m 这样的绝对容量。调度器的准入承诺和本机竞争权重必须分别建模。

    Linux v6.16 中，cpu_weight_write_u64() 会把 cgroup weight 转成调度器内部权重，再更新相应的 task_group。这个接口主要影响 fair-class scheduler 下的进程；实时调度类和使用自定义 sched_ext 的任务有各自边界，不能假定所有调度策略都遵守同一套 weight。

    cpu.max：在周期内消费配额#

    cpu.max 的格式是：

    $MAX $PERIOD

    默认值 max 100000 表示不限制。文中的 200000 100000 表示每个 100ms 周期最多消费 200ms CPU 时间。多线程可以在多核上并行消耗这份配额；配额耗尽后，对应的 fair scheduling run queue 会被 throttle，等下个周期补充 runtime 后再运行。

    cpu.stat 中的 nr_periods、nr_throttled 和 throttled_usec 可以说明限制是否频繁命中。只看 CPU 使用率不够：一个延迟敏感任务即使平均用量没到 2 CPU，也可能因为短时并发把配额提前耗尽，随后在周期尾部等待。

    cpu.max 控制时间，不控制位置。要限制任务只能在 CPU 2 和 3 上运行，应使用 cpuset.cpus；要独占 CPU，还需要 node agent 协调拓扑与其他工作负载，不能只写一个叶子文件。

    2.3 内存保护、回收与 OOM#

    CPU 时间用完后可以暂停，内存却带着状态。已经分配的匿名页、page cache、内核对象和 socket buffer 不会因为周期结束自动消失。memory controller 因此有一组不同强度的边界：

    文件 语义 超过边界后的动作
    memory.min 硬保护 有效 min 内不回收；没有其他可回收内存时可能导致 OOM
    memory.low 尽力保护 优先回收未保护组；必要时仍可回收 low 内页面
    memory.high 降速边界 对该组施加强回收压力并 throttle，不直接触发 OOM
    memory.max 最终硬边界 直接回收仍无法满足分配时，在该 memcg 内触发 OOM

    进程申请一页内存时，memory controller 会找到它所属的 memcg，沿层级更新 page counter。try_charge_memcg() 先尝试 charge；超过边界后进入直接回收，仍无法前进时才进入 memcg OOM。memory.high 的超额还会通过 mem_cgroup_handle_over_high() 把回收成本和等待施加给造成压力的任务。

    这条路径解释了几个常见现象：

    • memory.max 是硬边界，但 memory.current 在特殊情形下可以短暂超过它；内核需要先完成某些分配，再回收或选择 OOM victim。
    • memory.high 适合作为日常控制线。配置太低时，任务会逐渐变慢而不是马上死亡，资源管理器可以结合 pressure 调整它。
    • memory.oom.group=1 可以让 cgroup 被当作不可分割的工作负载。发生本组 OOM 时，内核会一起杀掉本 cgroup 及后代 cgroup 中的任务，而不是留下一个缺少关键子进程的半残实例；oom_score_adj=-1000 的任务例外。
    • 把运行中的进程迁到新 cgroup，不会把它以前申请的内存一并迁走。内存仍记在最初 charge 的 memcg 上，这也是内核文档建议“organize once and control”的原因。

    memory.swap.max 单独限制 swap 用量。把它设为 0 会阻止该组匿名内存继续换出，但不会让已经换出的页面凭空回到内存。它和 v1 的 memory+swap 联合上限不是同一种计数口径。

    2.4 I/O 限制与 writeback#

    io.max 按块设备的 major:minor 配置读写 BPS 或 IOPS：

    259:0 rbps=max wbps=52428800 riops=max wiops=max

    达到上限后，块层延迟后续 I/O；短暂 burst 是允许的。io.weight 则用于同一设备上兄弟 cgroup 的相对分配，实际效果依赖块设备、I/O scheduler 和启用的策略。

    直接 I/O 比较容易归属，因为提交路径带着发起任务的信息。buffered write 要复杂得多：应用只是把 page cache 标成 dirty，真正写盘可能由之后的 writeback worker 完成。cgroup v2 让 memory controller 提供 dirty page 所在的 memory domain，I/O controller 再负责 writeback 的 I/O domain。支持 cgroup writeback 的文件系统会据此归属 I/O；Linux v6.16 文档列出的实现包括 ext2、ext4、btrfs、f2fs 和 XFS，其他文件系统可能把 writeback 记到 root cgroup。

    归属也不是绝对精确。内存按 page 记账，writeback 主要按 inode 归属；多个 cgroup 同时写同一个 inode 时，一部分 I/O 可能记到当前主要 owner。顶层 API 如果承诺“某个目录严格只有 50MiB/s”，却不检查它背后的文件系统、块设备和共享方式，这个承诺很可能无法兑现。

    I/O controller 控制的是吞吐和竞争，不是存储容量。任务最多能写多少磁盘空间，仍要靠文件系统 quota、独立 volume、项目配额或上层清理策略。

    2.5 pids：在 fork 路径拒绝#

    pids.max 防的是 fork bomb 一类问题。每次 fork() 或 clone() 时，pids controller 会沿祖先链尝试增加计数；任何一级超过 limit，pids_try_charge() 都会回滚已经增加的计数并返回 -EAGAIN。

    这里的 PID 实际按内核 task，也就是 TID 计数。一个拥有 200 个线程的进程会消耗约 200 个名额，不能把 pids.max: 256 理解成“最多 256 个用户态进程”。

    通过修改限制或迁移进程，可以暂时看到 pids.current > pids.max；controller 保证的是新的 fork()/clone() 不能继续违反策略，而不是强行杀掉已有 task。命中次数可以从 pids.events 读取。

    2.6 统计、事件与 PSI#

    一个资源管理器至少要观察下面几类文件：

    目的 常见接口 能回答的问题
    存量与累计量 memory.current、memory.stat、io.stat、cpu.stat、pids.current 资源用了多少，组成是什么
    限制事件 memory.events、pids.events high、max、OOM 或 PID 上限命中过几次
    生命周期 cgroup.events 子树是否 populated，freeze 是否完成
    资源压力 cpu.pressure、memory.pressure、io.pressure 任务因为资源不足损失了多少可运行时间

    Pressure Stall Information（PSI）会给出 some 和 full 两行。some 表示至少有部分 task 因该资源停顿的时间比例；full 表示所有非 idle task 同时停顿，工作负载已经没有有效进展。每行包含 10、60、300 秒移动窗口和累计微秒数，还可以通过 poll()/epoll() 注册阈值触发器。

    这比只盯着 memory.current / memory.max 更接近用户感受。缓存型任务可能长期接近内存上限却没有压力；另一个任务用量不高，却可能频繁 direct reclaim。资源调整应同时看使用量、限制事件和 pressure，而不是把某个百分比当成唯一信号。

    还要划清一条容易混淆的边界：cgroup 不是容器的全部。容器通常把多种内核能力组合起来：

    目标 主要机制
    组织、记账和分配 CPU/内存/I/O/PID 等资源 cgroup
    隔离 PID、mount、network、UTS、IPC、user 等视图 namespace
    限制系统调用 seccomp
    控制对象访问 LSM，例如 SELinux、AppArmor
    拆分 root 权限 Linux capabilities
    构造 root filesystem 和挂载关系 mount namespace、pivot_root/chroot、VFS

    cgroup v2 的 device access 也不再提供 v1 那套 devices.allow/devices.deny 文件，而是通过 BPF_PROG_TYPE_CGROUP_DEVICE 程序决定某次 mknod、read 或 write 是否允许。它仍属于 cgroup 挂载点上的策略，但执行依赖 cgroup BPF。

    只创建 namespace 不能阻止容器耗尽宿主机内存；只创建 cgroup 也不能阻止进程看到宿主机 PID 或访问不该访问的文件。所谓“容器”来自这些机制和用户态生命周期管理的组合，内核里没有一个名为 Container 的总开关。

    3. 从 v1 到 v2：问题不只是文件名太乱#

    3.1 v1 为什么允许多层级#

    cgroup 最初随 Linux 2.6.24 发布。v1 允许创建任意多棵 hierarchy，每个 controller 只能绑定到其中一棵，一棵树也可以挂多个 controller。

    这套设计想解决一个真实需求：同一批进程可能需要按不同维度分类。大学服务器可以按教师/学生划分 CPU 和内存，却按网页浏览/NFS/其他流量划分网络。若强制所有资源共享一棵树，就要为这些分类的笛卡尔积创建大量 cgroup。

    于是，同一个进程在 v1 中可能同时拥有几条完全不同的路径：

    5:cpu,cpuacct:/users/student/batch
4:memory:/courses/video/transcode-7f3a
3:blkio:/io-priority/low

    局部看很灵活。系统规模变大后，用户态要同时维护多棵相似却不完全一致的树，controller 也无法假定自己与其他资源看见的是同一组进程。原本用来避免组合爆炸的设计，反过来把组合关系留给了每一个管理器和 controller。

    Linux 3.10 开始开发新的实现，早期需要 __DEVEL__sane_behavior 挂载选项；cgroup v2 随 Linux 4.5 正式发布。它没有尝试保留所有 v1 自由度，而是先收紧结构，再在明确边界内补回需要的能力。

    3.2 v1 的三类结构冲突#

    第一类冲突来自多棵树。v1 中一个 controller 同一时刻只能绑定到一棵 hierarchy。freezer 这类通用 controller 即使对多种分类都有用，也只能出现在一棵树中；树一旦填入 cgroup，controller 又很难移动。实践中，除了 cpu 和 cpuacct 这类天然相关的组合，很多系统只好为 controller 分别挂树。

    更棘手的是，CPU controller 无法知道 memory controller 看见的拓扑。两者必须假定彼此完全正交。buffered write 恰好同时横跨内存和 I/O：脏页先记在 memcg，之后才由 writeback 发往块设备。如果两套 controller 没有共同的资源域，归属与限速很难协调。

    v2 规定一棵 unified hierarchy。进程只有一个资源身份，controller 可以在同一层级上选择性启用；某个 controller 不关心更细粒度时，可以在较高节点停止继续分发，而不是另建一棵树。

    第二类冲突来自线程归属。v1 允许同一进程的线程进入不同 cgroup。对 CPU 线程池有时很有用，对内存、socket buffer、page cache 这类难以归属到单一线程的资源却说不通。更糟的是，应用为了管理自己的线程，需要解析 /proc/self/cgroup、拼出文件路径再读写伪文件；目标进程可能在这些步骤间被迁移，整个过程既繁琐又有竞态。

    v2 默认按进程迁移：向 cgroup.procs 写任意线程的 PID，会移动整个 thread group。确实需要线程级 CPU 分配时，可以显式创建 threaded subtree，通过 cgroup.type 和 cgroup.threads 管理。只有支持 threaded mode 的 controller 能在里面启用；Linux v6.16 文档列出 cpu、cpuset、perf_event 和 pids。内存等 domain resource 仍归到共同的 threaded domain。

    这不是删除线程级控制，而是把“系统管理的进程资源域”和“应用参与的线程调度”分成两个模式。

    第三类冲突出现在内部进程和子 cgroup 之间。v1 允许父 cgroup 自己放线程，同时把资源分给子 cgroup。此时父进程和子组是什么关系？

    • CPU controller 曾把内部线程和子 cgroup 当成同级竞争者。父级线程数一变，子组实际比例也跟着漂移。
    • I/O controller 为内部线程偷偷创建一层 hidden leaf，并暴露 leaf_ 前缀参数。
    • memory controller 没有一致办法定义父进程与子组怎样竞争。

    这类差异没法由某一个 controller 修好，因为问题来自树的结构。v2 的 no internal process 约束给出统一答案：非 root 的 domain cgroup 只要向子节点分发 domain controller，自己就必须为空。进程待在叶子，内部节点分配资源，两种实体不再同场竞争。

    threaded subtree 是经过约束的例外。它只接纳 threaded controller，并把无法归到线程的资源统一记到 thread root，因此没有回到 v1 的任意组合。

    3.3 v2 如何收紧层级与委托#

    在 v2 中，controller 要先出现在父节点的 cgroup.controllers，再由父节点写入 cgroup.subtree_control，子节点才能获得相应接口。非 root 节点也只能继续分发父级已经分给它的 controller。

    资源参数同样沿层级生效：

    • 子级 memory.max 无法突破祖先的 memory 上限。
    • memory.low/memory.min 的有效保护量受祖先分配的保护额度约束。
    • CPU weight 先在父级的直接子节点间分配，每个子节点再分自己的份额。
    • pids.max 在任意祖先命中都会阻止新的 task 创建。

    这使“把 team-video 委托给另一个管理器”成为可推理的操作。被委托者可以在子树内建组和分配资源，却不能凭空得到父级没有授予的 controller；即使把子级文件写得更宽，实际可用资源也越不过祖先边界。

    资源分发之外，v2 还收紧了进程迁移的权限边界。v1 的非特权委托缺少完整的 containment。v2 要求迁移进程的人同时拥有目标 cgroup.procs 和源、目标公共祖先的 cgroup.procs 写权限；cgroup namespace 还要求两端都能从当前 namespace 到达。被委托者因此可以在自己的子树内移动进程，却不能把外部进程拉进来，或把受限进程推出去。

    在 systemd 主机上还要再加一条用户态规则：一棵子树只有一个 writer。PID 1 管整棵系统树，容器管理器或自研 agent 必须通过 service/scope 的 Delegate= 获得明确子树；双方不能同时创建、删除或迁移同一范围内的 cgroup。Kubernetes 推荐 systemd cgroup driver，根本原因也在这里：kubelet/runtime 与 PID 1 需要对层级所有权形成一致视图。

    3.4 v2 的接口与语义变化#

    v2 约定 controller 文件使用 <controller>.<parameter> 命名，无上限统一写 max，权重统一使用 1 到 10000、默认 100，统计多采用按 key 解析的文本格式。cgroup.events 提供递归的 populated/frozen 状态，PSI 提供资源停顿信息，避免继续依赖 v1 release_agent 那类每次事件启动用户态 helper 的机制。

    迁移不能靠批量改名：

    cgroup v1 cgroup v2 迁移时不能忽略的差异
    cpu.shares cpu.weight 取值范围和默认值不同，必须转换；weight 仍只在兄弟争用时生效
    cpu.cfs_quota_us + cpu.cfs_period_us cpu.max 两个文件合成 $MAX $PERIOD，带宽语义基本对应
    cpuacct.usage 等 cpu.stat cpuacct 并入 CPU controller，字段和单位要按 key 读取
    memory.soft_limit_in_bytes 没有严格等价项，通常重新设计为 memory.low/memory.high v1 soft limit 非层级化；v2 low 是保护，high 是降速边界
    memory.limit_in_bytes memory.max 下调到当前用量以下时，v2 可能同步回收并触发 memcg OOM
    memory.memsw.limit_in_bytes memory.max + memory.swap.max v1 限制 memory+swap 总和；v2 单独限制内存和 swap
    blkio.throttle.* io.max v2 使用单个按设备、按 key 的接口，buffered write 归属能力也不同
    freezer.state cgroup.freeze + cgroup.events 发起 freeze 与观察完成状态分开
    tasks 默认使用 cgroup.procs；threaded subtree 使用 cgroup.threads v2 默认按整个进程迁移
    notify_on_release + release_agent cgroup.events + poll/inotify 不再为每个 release 事件执行 helper
    devices.allow/devices.deny cgroup device BPF v2 没有对应接口文件
    net_cls、net_prio 没有直接等价 controller 按需求迁移到 cgroup BPF、tc 或其他网络策略层

    cpu.shares -> cpu.weight 特别能说明为什么上层不该保存内核旋钮。早期 OCI runtime 常用线性公式把 [2, 262144] 映射到 [1, 10000]，会把 v1 默认 shares 1024 映射到约 39，而不是 v2 默认 weight 100。runc 1.3.2 和 crun 1.23 开始采用经过三个基准点的新公式。Kubernetes API 的 500m 没有变化，变化发生在 runtime 的实现层。监控如果把换算结果当成用户意图，升级后就会产生假告警。

    4. 怎样迁移一个真正使用 cgroup 的系统#

    如果系统只通过成熟 runtime 或 systemd 配置资源，迁移主要发生在操作系统和 runtime 层。如果代码直接读取 /sys/fs/cgroup，就要把它当成一次 backend 重写。

    4.1 盘点 cgroupfs 依赖#

    容易漏掉的调用者不只有容器运行时：

    • 监控 agent 可能硬编码 v1 mount path 和统计文件名。
    • JVM、Node.js 或语言库可能从 cgroup 计算可用 CPU 与堆上限。
    • 安全 agent 可能依赖 devices、net_cls 或进程路径。
    • 运维脚本可能读取 cpuacct.usage，或用 release_agent 清理目录。
    • 应用可能把宿主机 cgroupfs 挂进容器并自行调整子组。

    Kubernetes 文档列出了 cAdvisor、JDK、Node.js 和 automaxprocs 等容易漏查的组件。自研系统也该按同样思路盘点：任何直接解释 cgroupfs 的组件都在消费一套版本化内核 API。

    4.2 分离所有权与接口版本迁移#

    迁移步骤可以分成：

    1. 升级到默认启用 v2 的发行版，并确认 systemd、OCI runtime、监控和语言运行时版本支持 v2。
    2. 让一台测试节点只使用 unified hierarchy，避免长期停留在 hybrid mode。controller 不能同时属于 v1 和 v2，混合挂载会让能力判断更难。
    3. 统一 cgroup manager。systemd 主机选择 systemd driver，并确认上层 agent 只操作委托子树。
    4. 让 backend 根据 cgroup.controllers 和实际文件发现能力，不用内核版本号猜测。
    5. 对照资源意图验证行为，而不是只检查文件存在：制造 CPU 竞争观察 weight，触发 quota 观察 throttling，在可回收内存与不可回收内存场景下分别验证 high/max，检查 buffered I/O 与 PID 上限。
    6. 比较 status、统计和告警。重点检查单位、层级聚合、OOM 范围、swap 口径、CPU weight 转换和 pressure 指标。
    7. 编排系统优先新增 v2 节点池、迁移工作负载再淘汰 v1 节点。直接切换已经运行节点的 cgroup driver，容易让 runtime 无法找到旧 sandbox 的层级。

    有 Linux 节点时，可以用下面的接口确认模式：

    stat -fc %T /sys/fs/cgroup/

    输出 cgroup2fs 表示 v2；v1 根通常显示 tmpfs。对程序来说，statfs() 的 CGROUP2_SUPER_MAGIC 比解析 mount 文本更可靠。还可以检查 /sys/fs/cgroup/cgroup.controllers 是否存在，并从 /proc/$PID/cgroup 读取进程路径；v2 条目固定形如：

    0::/team-video/transcode-7f3a/main

    这些命令只能确认接口版本和归属，不能证明资源策略正确。最终仍要观察 controller 文件、事件和负载行为。

    5. 回到最初的系统设计#

    如果现在要实现一个基于 cgroup 的软件系统，我会把边界定在下面四层：

    1. ResourceSpec 只表达可移植的意图：调度承诺、竞争权重来源、降速边界、硬上限、OOM 范围和可观测状态。设备号、周期默认值和 cgroup 文件名不进入公开 API。
    2. admission/scheduler 负责全局承诺。CPU 和内存 request 是否超卖、memory protection 能否沿祖先兑现、独占 CPU 和 volume 放置，都不能交给 cgroup 临场解决。
    3. node agent 负责一棵有明确所有权的层级，通过可替换 backend 生成并执行 ResourcePlan。它要先构造空的内部节点，再让进程直接进入叶子，并持续 reconcile。
    4. 反馈回路同时读取 usage、events 和 PSI。CPU throttle、memory high/OOM、I/O pressure 和 PID 拒绝要进入 workload status，供扩缩容、迁移、降级或终止策略使用。

    有几种设计应当直接拒绝：

    • 让每个插件都能在同一棵 cgroup 树里创建和移动节点。
    • 把 memory.request 宣传成硬预留，却不管理父级 memory.min/memory.low 预算。
    • 用 CPU 使用率替代 throttle/pressure，或用内存百分比替代 reclaim/OOM 事件。
    • 启动进程后过一段时间才迁入 cgroup。
    • 把 v1 文件名替换成 v2 文件名，却保留旧的 soft limit、swap、thread 和 delegation 假设。
    • 遇到不支持的 controller 时静默降级，同时仍把 workload 标成 Ready。

    到这里再看 Kubernetes 的四个数字，它们就不再神秘。API server 保存的是用户意图，scheduler 处理节点容量，kubelet 与 runtime 把意图翻译成本机层级和参数，Linux 的调度器、内存管理与块层才执行最后的竞争、回收、降速和拒绝。cgroup 是这条链上很低的一层，但系统能否给出可信的资源承诺，取决于上面的每一层有没有把自己的职责说清楚。
